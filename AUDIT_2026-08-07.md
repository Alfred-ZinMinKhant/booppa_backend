# Booppa Full-Stack Consistency & Compliance Audit
**Date:** 2026-08-07 · **Scope:** `booppa_backend` + `booppa-nextjs` (working trees as-is)

## Method & honest coverage statement

- Backend routes enumerated by **importing `app.main:app`** — 821 route entries (~410 logical
  endpoints, dual-mounted at `/api` and `/api/v1`), not regex-guessed.
- Frontend: 146 pages, 344 TS/TSX files, 114 Next.js route handlers acting as a BFF proxy.
  All `/api/...` literals and `${config.apiUrl}...` templates extracted and joined against
  the backend route table.
- **Every finding below was opened and confirmed at the cited `file:line`.** Where I inferred
  rather than confirmed, it is marked `[INFERRED]`.
- **What this audit did NOT cover** (be aware before treating it as complete): per-page UI
  walkthrough of all 146 pages; runtime/DB verification against production; N+1 and index
  analysis; bundle-size and dependency-tree analysis; the `cms_admin/`, `contracts/`,
  `hardhat/`, and `infra/` trees. Findings are therefore a **floor, not a ceiling**.

## Executive Summary

**Health score: 62 / 100.**

This is not a sloppy codebase. Several things I expected to be broken are properly built, and
that is worth stating plainly because it changes where you should spend effort:

- Stripe webhook handling is **correct** — signature verification with a hard fail on missing
  secret, atomic `INSERT … ON CONFLICT` idempotency keyed on the Stripe event id, and an explicit
  rollback wrapper so a handler crash doesn't permanently consume the event.
- The email suppression / one-click-unsubscribe system is **genuinely well engineered** — a single
  choke point ahead of provider selection, so it covers the SES fallback as well as Resend, and
  12 of 12 recurring customer digests correctly pass `category="marketing"`.
- The RFP result page **refuses to fake progress**. It will render an error rather than claim
  "Generating…" without positive proof. That is the exact discipline this audit was looking for.
- Enterprise org endpoints enforce real membership/ownership checks (`_get_org`) before the
  plan gate. No IDOR found there.
- No committed secrets, no f-string SQL, constant-time admin credential comparison.

The problems are concentrated in three places: **(1) one whole product surface is
unauthenticated and its access gate is frontend-only, (2) a compliance control sold to
Enterprise customers does nothing, and (3) the cold-outreach engine is not compliant with
Singapore's Spam Control Act.**

**Production readiness:** the core purchase→fulfilment path is production-ready. The government
portal is not. The SCOUT outreach engine should be **paused today** until P0-3 is fixed.

**Critical blockers (P0):** 3 · **High (P1):** 9 · **Medium (P2):** 8

**Cross-cutting theme.** Your own `CLAUDE.md` defines commercial readiness as three layers, and
warns that layer 3 — *what the regulator actually requires* — is the one that gets skipped, with
the specific trap being "a written policy with no test evidence is not a control." Every P0 below
is a layer-3 failure of exactly that shape: a control that exists as a UI affordance or a database
row, with nothing behind it. For a company selling compliance, these are not ordinary bugs — they
are the product failing its own thesis.

## Critical Issues (P0)

### P0-1 — The entire Government Portal is unauthenticated; its access gate exists only in the browser

**Files:** `app/api/government.py` (whole module), `app/api/government/register/route.ts:53`,
`components/government/GovernmentLandingPage.tsx:11, 208, 546`

Three compounding defects:

1. **No authentication on any data endpoint.** `government.py` contains **zero** auth imports —
   no `get_current_user`, no `oauth2_scheme`, no `Security`. All six data endpoints take only
   `db: Session = Depends(get_db)`:
   `GET /vendors`, `GET /vendors/{uen}`, `GET /tenders`, `GET /stats`,
   `POST /verify`, `POST /shortlist-report`.
   Anyone on the internet can pull the full vendor intelligence set and generate AGO-auditable
   shortlist reports without an account.

2. **The `.gov.sg` restriction is commented out server-side.** `government.py:127-136`:
   ```
   NOTE: .gov.sg domain check is disabled for testing.
   To enable, uncomment the domain validation block below.
   ```
   The check lives only in `GovernmentLandingPage.tsx:208` and the Next proxy at
   `register/route.ts:53`. A direct `POST https://api.booppa.io/api/government/register`
   mints a `role="GOVERNMENT"` account for any email address.

3. **The UI states the restriction as fact.** "Access is restricted to Singapore government
   email addresses ending in .gov.sg" and "access is provisioned automatically within minutes"
   (`GovernmentLandingPage.tsx:208, 546`).

**Impact.** A registration form collects names, agency affiliations and passwords from public-sector
officers under a stated access-control representation that does not exist, to gate data that is
already public. That is a false security representation to government users, an authorization
gap, and a privilege-escalation path in one page.

**Fix.** (a) Uncomment and enforce the domain check server-side. (b) Add
`Depends(get_current_user)` + a GOVERNMENT-role check to all six data endpoints, or explicitly
document them as a public dataset and remove the registration gate entirely. (c) Only then
reconcile the landing-page copy. Do not fix (c) first.

### P0-2 — Enterprise data-retention policies are stored and never enforced

**Files:** `app/core/models.py:1366-1373`, `app/api/enterprise_api.py:329-342`

`RetentionPolicy` carries `data_category`, `retention_days`, `auto_purge`. Customers create and
list them through the Enterprise API. A grep across the entire `app/` tree finds **no other
reference to the model or to `auto_purge`** — no Celery task, no entry in the ~38-job beat
schedule, no purge routine anywhere. `auto_purge=True` has never deleted a byte.

**Impact.** An Enterprise buyer configures a data-retention control, the API returns 201, and
the UI confirms it. When that buyer's own regulator asks them to evidence retention enforcement,
they will point at Booppa. This is your `CLAUDE.md` layer-3 trap stated literally: documented,
never tested, not a control.

**Fix.** Either implement a scheduled purge task honouring `retention_days`/`auto_purge`, or
remove the endpoints and the UI until it exists. A third option — labelling it "policy record
only, not enforced" in the UI — is defensible but must be explicit.

### P0-3 — SCOUT cold outreach is not compliant with the Spam Control Act (Cap. 311A)

**Files:** `app/workers/scout_celery_tasks.py:330-365`, `app/services/scout_outreach_templates.py`,
`app/services/email_layout.py:78-80`, `app/services/scout_shared.py:257+`

The system sends unsolicited commercial email in daily-capped bulk batches to `contact_email`
addresses **scraped from prospect websites**. Against the Act's Second Schedule requirements:

| Requirement | Status |
|---|---|
| `<ADV>` as the first characters of the subject line | **Absent** — subjects built at `scout_outreach_templates.py:50, 96, 122` |
| Unsubscribe facility **within the message**, valid ≥30 days | **Absent** — only the SMTP `List-Unsubscribe` header (`resend_email.py:128-134`); rendered footer is `email_layout.py:78-80` |
| Accurate, functional **postal address** of the sender | **Absent** — footer reads "BOOPPA Intelligence · Singapore · booppa.io" |

Two aggravating defects in the same path:

- **`Dear [Name],` ships literally.** `scout_outreach_templates.py:53, 98, 124`.
  `scout_shared.py:261` calls it "a manual-fill placeholder", but **no code path fills it**:
  `POST /scout/approve` (`scout_approval_api.py:93-109`) is a bulk status flip, and no endpoint
  exists to edit `outreach_body_html`. Every recipient gets "Dear [Name],".
- **The email asserts compliance gaps the scan did not find.** `generate_vendor_outreach`
  lines 32-33: when fewer than two checks fail, it pads the list with the generic strings
  "a PDPA compliance gap" and "your data protection policy" — then presents them under
  *"The two most urgent gaps identified on your public-facing site."* This directly contradicts
  the `absence_of_evidence_invariant` you already established for the PDPA product, and it is
  an unverified negative assertion about a **named third party**, sent to that party alongside a
  ranking against its competitors.

Also: `approve_batch` leaves `approved_by_user_id` NULL by design (comment, line 102). For a
consent-sensitive bulk send to scraped addresses, a bare timestamp is a weak authorisation record.

**Impact.** Each non-compliant message is separate exposure under an Act that creates a private
right of action, sent by a company whose product is PDPA compliance. The defamation-adjacent risk
from asserting non-existent gaps is the sharper edge.

**Fix.** Pause `scout_send_approved_batch_task`. Then: `<ADV>` subject prefix; render a real
unsubscribe link (reuse `make_unsubscribe_token`) and the registered postal address in
`branded_email_html` for `category="marketing"`; never assert an undetected gap; add a
body-edit endpoint or drop the `[Name]` salutation; record the approving admin.

## High Priority (P1)

### P1-1 — Five enterprise/SSO endpoints 404 because the BFF omits the `/api` prefix
`config.apiUrl` is `https://api.booppa.io` with no path, and the backend mounts **only** at
`/api` and `/api/v1` (`app/main.py:186-187`). 74 of 79 call sites build `${config.apiUrl}/api/...`
correctly. These five do not:

| File:line | Built URL | Route that exists |
|---|---|---|
| `app/api/enterprise/organisations/route.ts:12` | `/enterprise/organisations` | `/api/enterprise/organisations` |
| `app/api/enterprise/seats/route.ts:25` | `/enterprise/organisations/{id}/seats` | `/api/enterprise/organisations/{org_id}/seats` |
| `app/api/enterprise/sso/route.ts:31,44` | `/enterprise/organisations/{id}/sso` | `/api/enterprise/organisations/{org_id}/sso` |
| `app/api/sso-discover/route.ts:18` | `/enterprise/sso/discover` | `/api/enterprise/sso/discover` |

These are *specific* Next routes, so they win over the sibling `enterprise/[...path]` catch-all,
which builds the URL correctly. Worst case: `sso-discover` defaults its body to `{options:[]}`,
so the login page silently shows "no SSO available" — **an SSO customer cannot log in, and
nothing is logged.**

### P1-2 — Bundle purchases have no intake-recovery path; the buyer lands on an error page
`stripe_checkout.py:1086-1088` marks five product types as requiring a brief. The lazy
`PendingRfpIntake` recovery at **line 1172** covers only `rfp_complete` and `rfp_express`.
If the webhook races or fails for `rfp_accelerator`, `enterprise_bid_kit`, or
`compliance_evidence_pack`, verify returns `requires_brief=true, pending_rfp_intake_id=null`,
the result page exhausts its 3 retries and calls `setStatus('error')`
(`app/rfp-acceleration/result/page.tsx:259-261`). **The two cheapest SKUs are protected; the
three most expensive are not.** Fix: drive both branches off one shared constant.

### P1-3 — "Evidence accessible for 90 days after cancellation" is unimplemented
`app/pricing/page.tsx:23-24`, `app/csp/page.tsx:278, 289`. Cancellation handling in
`stripe_webhook.py` (~900-1000) downgrades `user.plan`, refreshes `max_seats`, deactivates SSO,
marks the `Subscription` row canceled. There is no grace window anywhere in `app/` — plan-gated
readers lose access the moment the plan changes. Either implement a `cancelled_at + 90d` read
grace in the entitlement check, or correct the pricing copy.

### P1-4 — Real-time notifications have never worked
`components/notifications/NotificationProvider.tsx:55` fetches `/api/auth/ws-token`. The route
that exists is `app/api/ws-token/route.ts` — no `/auth` segment — and no backend route matches
either. The 404 is swallowed by `if (!res.ok) return`. The socket.io client never initialises;
`enterprise_visited` and `verify_completed` have never fired. The backend `socket.io` mount
(`main.py:190`) and its emitters are dead weight. The handlers are also still in Italian
("ha aperto il link di verifica") and would render to users if revived.

### P1-5 — `ws-token` hands the full session JWT to client JavaScript
`app/api/ws-token/route.ts` documents itself as returning a "token SHORT-LIVED" that creates no
new secrets. It returns the raw `token` cookie verbatim — the 7-day access JWT
(`config.tokenMaxAge`). The cookie's HttpOnly protection is deliberately defeated by an endpoint
any same-origin script can call. Currently unexploited only because its sole caller (P1-4) is
broken — so fix this **before** fixing P1-4. Mint a short-lived, WS-scoped token instead.

### P1-6 — QR-code vendor verification always fails
`app/qr-scan/page.tsx:39` fetches `/api/v1/vendors/{slug}`, which does not exist. The real routes
are `/api/marketplace/vendor/{slug}` and `/api/passport/{vendor_uen}`. Every scan of a printed
Booppa badge renders "Vendor profile not found." This is the physical trust artefact customers
put on their collateral.

### P1-7 — Enterprise bulk vendor-request flow always fails
`app/api/enterprise/bulk-request/route.ts:54` POSTs `/api/v1/enterprise/send-requests`; no such
backend route exists. Result: `throw new Error('Backend request failed')` on every attempt.

### P1-8 — No rate limiting on authentication endpoints
`app/core/limiter.py:24` sets a global default of `200/minute` per IP. Only **two** endpoints add
their own limit (`stripe_checkout.py:436, 944`). `app/api/auth.py` imports the limiter on line 1
and never uses it. Login, register, and password-reset therefore allow ~12,000 attempts/hour/IP —
credential stuffing and reset-token brute-forcing are both practical. `POST /api/government/register`
has no backend limit at all; its only protection is an in-memory `Map` in the Next proxy
(`register/route.ts:6-18`) that is per-instance, resets on cold start, and is bypassed entirely
by calling the backend directly.

### P1-9 — Mock report generator is publicly reachable in production
`app/api/__init__.py:191` mounts `mock_report_router` at `/mock`. `GET https://api.booppa.io/api/mock/report`
returns, unauthenticated, a full PDF rendered by the **real** `PDFService` carrying a fabricated
`tx_hash` and a `verify_url` pointing at the live Polygon explorer (`app/api/mock_report.py:14-28`).
The hash is structurally invalid (36 hex chars, not 64), which is the correct instinct per your
`demo_tx_hash_must_fail_shape_gate` rule — but a document that looks like a genuine Booppa
compliance certificate should not be mintable by anonymous strangers. Gate behind admin auth or
drop the router in production.

**Sprint 1 — Critical (do first; the first item is same-day)**
1. Pause `scout_send_approved_batch_task`. (P0-3)
2. Uncomment the server-side `.gov.sg` check; add authn/authz to all six government data
   endpoints. (P0-1)

4. Fix the three Spam Control Act items and the `[Name]` / phantom-gap defects, then resume SCOUT. (P0-3)

**Sprint 2 — Important**
5. Add `/api` to the five enterprise/SSO BFF calls; then normalise all 79 call sites onto one
   base-URL convention so this class cannot recur. (P1-1, P2-6)
6. Drive bundle intake recovery off the shared `requires_brief` constant. (P1-2)
7. Per-endpoint rate limits on login / register / password reset / government register. (P1-8)
8. Replace the `ws-token` passthrough with a short-lived WS-scoped token, **then** fix the
   NotificationProvider path. (P1-5 before P1-4)

10. Point `qr-scan` at `/api/marketplace/vendor/{slug}`; build or remove `send-requests`. (P1-6, P1-7)
11. Gate or drop `/api/mock/report`. (P1-9)

**Sprint 3 — Improvements**
12. Add `/api/track`, or remove the calls. (P2-1)

15. Translate the Italian notification layer; fix `<a href>` PDF error handling. (P2-8, P2-5)
