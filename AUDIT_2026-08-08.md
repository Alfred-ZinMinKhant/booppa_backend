# Part B — New findings

## 🚨 P0-A — An unauthenticated public route mints Stripe sessions with a client-chosen price, and the backend grants entitlement from client-chosen metadata

**Frontend:** `booppa-nextjs/app/api/checkout/create-session/route.ts` (whole file, 39 lines)
**Backend:** `app/api/stripe_webhook.py:274, 300-330`
**Endpoint:** `POST https://booppa.io/api/checkout/create-session`

**Current behaviour.** The route takes `priceId`, `mode`, `metadata`, `successUrl`, `cancelUrl`
straight from the request body and passes them to `stripe.checkout.sessions.create` using the
live `STRIPE_SECRET_KEY` (`:4`). There is **no authentication, no allow-list, no
product↔price check, and no rate limit.** It is not referenced anywhere in the frontend — it is
dead code that is nonetheless deployed and live.

Downstream, `stripe_webhook.py:274` reads `product_type = metadata.get("product_type")` and
`:300` activates the subscription on that value alone. `amount_total`, the line item's price, and
even `session.mode` are never consulted.

**Failure scenario (concrete).**
```
POST /api/checkout/create-session
{ "priceId": "<NEXT_PUBLIC_STRIPE_NOTARIZATION_ADDON_1>",   // SGD 29, shipped in the client bundle
  "mode": "payment",
  "metadata": { "product_type": "pro_suite_monthly", "customer_email": "attacker@example.com" },
  "successUrl": "https://booppa.io/", "cancelUrl": "https://booppa.io/" }
```
Attacker pays **SGD 29**. Stripe fires `checkout.session.completed`. The webhook reads
`product_type = "pro_suite_monthly"`, finds it in `SUBSCRIPTION_PRODUCT_TYPES`, and calls
`_activate_subscription` — granting the **SGD 4,500/month Pro Suite** (SSO, MAS TRM baseline,
board report white-label, 100 notarizations). `NEXT_PUBLIC_STRIPE_*` price IDs are public by
construction, so no insider knowledge is needed. The same substitution works for every SKU.

**Customer/business impact.** Total revenue integrity failure on every paid product; the most
expensive tiers are the most attractive targets. It also lets an attacker create Stripe sessions
against your account at will (unauthenticated, unmetered) — a Stripe-side abuse and
reconnaissance surface independent of the entitlement bug.

**Fix.** (a) Delete `app/api/checkout/create-session/route.ts` — nothing references it, so this is
a zero-risk change and should ship today. (b) In `stripe_webhook.py`, before granting anything,
resolve the session's actual line-item price and assert it equals `_get_price(product_type)`;
refuse and alert via `_alert_payment_fulfillment_issue` on mismatch. (b) is the real fix — (a)
alone still leaves P0-B.

## 🚨 P0-B — The backend checkout endpoint accepts a client-supplied `priceId` and never binds it to the product

**Backend:** `app/api/stripe_checkout.py:459`, `:786-788`, `:857`, `:890`
**Endpoint:** `POST /api/stripe/checkout`

```python
459:  price_id = data.get("priceId") or data.get("price_id")
...
786:  if not price_id:
787:      price_id = _get_price(product_type)      # only a FALLBACK
...
857:  metadata = {"product_type": product_type or "", ...}
890:  line_items=[{"price": price_id, "quantity": 1}],
```

A client-supplied `priceId` **wins** over the server's own mapping, while `metadata.product_type`
— the value that drives all downstream entitlement — is taken from a different body field. The
two are never cross-checked. This endpoint does require a valid access token (`:447-450`), so the
attacker must hold an account; that is the only difference from P0-A.

Two frontend call sites already exercise this shape
(`app/blog/singapore-courts-blockchain-evidence-2025/page.tsx:22` and the sibling blog page send
`{ priceId: PRICE_ENV, productType: 'quick_fix' }` — `quick_fix` is not in `MODE_MAP`, so it
silently falls through to `mode="payment"` and no webhook handler matches, logging
`no handler matched` at `stripe_webhook.py:380`). So these two CTAs take money and deliver
nothing — **P1 in its own right, listed as P1-1 below.**

**Fix.** Delete the `priceId` body field entirely; resolve price only via `_get_price(product_type)`
and 400 on unknown `product_type`. Fix the two blog CTAs to send a real SKU.

Reproduced locally: the reference DB is at `2026_08_05_0001`, head is `2026_08_08_0007`, and
**26 of 102 tests in `tests/checkout` + `tests/billing` fail** with:

```
psycopg2.errors.UndefinedColumn: column "plan_lapsed_at" of relation "users" does not exist
[SQL: INSERT INTO users (id, email, ..., plan, plan_lapsed_at, lapsed_plan, ...)]
```

That is not a schema-drift curiosity — SQLAlchemy emits **every mapped column** in every
`SELECT`/`INSERT` against `users`. If the new image reaches ECS before migration `0007`, *every*

degradation. Migration `0006` similarly gates the retention purge: without
`retention_purge_logs`, the daily beat job raises and P0-2's fix — including the dry-run log rows
that are its layer-3 evidence — silently never runs.

**UNVERIFIED:** production's current `alembic_version`. Confirm with
`select version_num from alembic_version` through `scripts/db_tunnel.sh` **before** the next
deploy. Per `CLAUDE.md`, a 401-instead-of-404 response proves only that code deployed and says
nothing about schema.

**Fix.** Dispatch `ci.yml` with `run_migrations=true` and verify `2026_08_08_0007` is stamped
*before* merging/deploying the code that maps those columns.

## 🔴 P1-2 — Any report is readable by anyone with the ID, and logging *out* grants more access than logging in

**Backend:** `app/api/reports.py:556-566`, `:603-621`, `:679-690`

```python
current_user: User = Depends(get_optional_user)
report = ReportRepository.get_by_id(db, str(report_id))
if report and current_user and report.owner_id != current_user.id:
    report = None
```

When `current_user` is `None` the ownership clause short-circuits and the report is returned in
full — PDF download included, via a fresh presign. An **authenticated non-owner gets 404; an
anonymous stranger gets the document.** Logging out strictly widens access.

Report IDs are UUID4, so this is a capability-URL design rather than an enumeration hole, and the
docstring says "public reports accessible by ID" — it is deliberate. Two things make it a finding
anyway: (a) the asymmetry is certainly not deliberate and is the shape that bites when an ID leaks
into a referrer, a support ticket, or a shared link; (b) `app/privacy/page.tsx:132` states
role-based access controls as a security measure to customers whose PDPA scan findings are in
these documents.

**Fix.** Make anonymous access an explicit, separate capability (a signed share token), and make
the ownership check unconditional for the account path: `if not report or (current_user and ...)`
→ `if not report or report.owner_id != current_user_id`.

## 🔴 P1-3 — No handling for failed renewals or chargebacks; refunds do not revoke anything

**Backend:** `app/api/stripe_webhook.py:1055-1099` (only `charge.refunded`), `:693-704`

- **`invoice.payment_failed` is not handled anywhere.** A customer whose card fails keeps full
  entitlement for Stripe's entire retry schedule, and Booppa sends no dunning notice. Access is
  eventually revoked only when Stripe gives up and fires `customer.subscription.deleted`.
- **`charge.dispute.created` / chargebacks are not handled at all** (grep: zero occurrences of
  `dispute`). A customer can charge back and retain the plan indefinitely.
- **`charge.refunded` writes a bookkeeping flag and nothing else** (`:1076-1085`
  `_set_assessment_values({"refunded": True, ...})`). Grep confirms the `refunded` flag is read
  only by `app/api/admin.py:571` for display — **it gates no read path anywhere.** A refunded
  subscription's plan is not downgraded, notarization credits are not clawed back, and the
  deliverable stays downloadable.

**Fix.** Add `invoice.payment_failed` (notify + start a defined dunning window) and
`charge.dispute.created` (suspend entitlement pending resolution). Decide explicitly whether a
refund revokes access and implement whichever answer the Terms state — today the code has no
answer.

## 🔴 P1-4 — The government portal is a shell: its flagship export 404s, and its authenticated calls cannot authenticate

**Frontend:** `components/government/BuyerDashboard.tsx:507, 818, 829, 838, 857`,
`components/government/GovernmentLandingPage.tsx:154, 406`
**Backend:** `app/api/government.py` (six endpoints, now correctly gated — and never called)

Three compounding problems:

1. **`POST /api/v1/reports/gov-shortlist` does not exist.** Confirmed against the imported route
   table. Every click of "Export AGO-auditable shortlist" — the capability the landing page sells
   at `GovernmentLandingPage.tsx:247` and the OG description advertises as
   "Export AGO-auditable shortlists" — throws `Export failed (404)`. The working implementation,
   `POST /api/government/shortlist-report` (`government.py:600`), is called by nothing.
2. **Cookie auth cannot work.** All six of the dashboard's direct-to-backend calls use
   `credentials: "include"` with **no `Authorization` header**, but the backend's `oauth2_scheme`
   is `OAuth2PasswordBearer` with no cookie fallback (`app/core/db.py:24, 68-77`). So
   `GET /auth/me` (`:818`) always 401s, `userEmail` is never populated, and the export payload's
   `generated_by_email` — the officer attribution on an *AGO audit artefact* — would be empty even
   if the route existed. These six are the **only** client-side cookie-only backend calls in the
   whole frontend; everywhere else proxies through the BFF, which forwards Bearer correctly.
3. **P0-1's fix therefore changes nothing a government user sees.** The dashboard reads
   `/marketplace/search`, `/marketplace/industries`, `/marketplace/stats` and
   `/gebiz/latest-tenders` — all unauthenticated (`app/api/marketplace.py:20, 63, 77`). That is
   defensible (it is the public vendor directory), but it means the entire `government.py` module
   is now dead code behind a lock, and the "restricted access" story is still not the story the
   UI actually implements.
4. **New false claim:** `GovernmentLandingPage.tsx:406` — "A verification link will be sent
   immediately." `gov_register` (`government.py:177-217`) sends no email; it returns tokens
   directly.

**Fix.** Decide whether the portal is authenticated. If yes: route the dashboard through a BFF
proxy that forwards Bearer, and point it at `government.py`'s endpoints including
`/government/shortlist-report`. If no: delete `government.py`'s gated endpoints and the
registration flow, and correct the landing copy. Either way, fix the "verification link" sentence.

## 🔴 P1-5 — `price_id` is reassigned by the duplicate-subscription guard and leaks into the new session

**Backend:** `app/api/stripe_checkout.py:591-592` and `:786-788, 890` (same function scope,
`checkout_post`)

The Stripe-by-email duplicate guard loops over the customer's existing subscription items and
assigns to the **same local `price_id`** the checkout later uses:

```python
591:  price_id = (item.get("price") or {}).get("id")
592:  if price_id and price_id in expected_prices:  raise HTTPException(409, ...)
```

When the price does **not** match `expected_prices`, no exception is raised and the loop exits
with `price_id` holding *another product's* Stripe price. Line 786 only overwrites it
`if not price_id` — it is truthy — so line 890 charges that price. A customer who holds any
active subscription for a different product can be charged the wrong amount on their next
purchase, and the metadata still names the product they asked for.

This is the same local-shadowing class already recorded twice in `stripe_webhook.py`
(see `local_test_setup` memory).

**Fix.** Rename the loop variable (`item_price_id`). Then add the P0-B binding assertion, which
would have made this unexploitable.

## 🔴 P1-6 — Booppa's own stated retention schedule is not enforced by anything

**Frontend:** `app/privacy/page.tsx:93-105` **Backend:** `app/services/retention.py:88`

The privacy policy publishes a six-line retention schedule (account data 7 years, transactions
7 years, reports 5 years, notarization hashes indefinite, **server logs 90 days**, marketing
consent +3 years) and states: *"Data is securely deleted or anonymized upon expiry of the
applicable retention period."*

The only purge that exists is the Enterprise-customer one, whose `RETENTION_CATEGORIES` covers
exactly three org-scoped tables: `sla_logs`, `webhook_deliveries`, `expired_invites`. Nothing
purges account data, transactions, reports, or logs on Booppa's own schedule.

This is P0-2 one level up: the layer-3 trap the retention fix closed *for customers* is still
open *for Booppa*. Most lines are not yet due if the company is under five years old — but the
90-day server-log line is due continuously.

**UNVERIFIED:** CloudWatch log group retention may already satisfy the 90-day line. Check
`aws logs describe-log-groups --query 'logGroups[].{n:logGroupName,r:retentionInDays}'`.

**Fix.** Either implement the schedule (an anonymisation job for the account/transaction lines,
a CloudWatch retention setting for logs) or amend the policy to describe the process that
actually exists. Note the DSAR routes (`privacy/page.tsx:109, 127`) are manual-by-email, which is
legally fine and not a finding.

# Verdict

## 🔴 NO-GO

Not because the product is bad — the fulfilment pipeline, the email suppression layer, the
identity-provenance discipline and yesterday's remediation are all genuinely above the bar for a
company this size. The blocker is narrow and specific:

1. **P0-A is exploitable right now** by anyone who reads your client bundle, and it converts the
   most expensive subscription you sell into a SGD 29 purchase. It is one file deletion plus one
   assertion away from closed.
2. **P0-C makes the next deploy an outage** unless the migration workflow is dispatched first.
3. **P1-1 means two live paid-acquisition pages take money and deliver nothing.**

Fix items 1–5 of Sprint 1 — realistically a day's work, and item 1 is a deletion — and this
becomes a **🟡 CONDITIONAL GO** pending the Sprint 2 government-portal and refund/dispute work.

**Answering the audit's own final question** — *would I pay the advertised price for what this
actually delivers?* For the PDPA scans, RFP kits, evidence packs and Vendor Proof: **yes**. Those
products deliver, and they fail honestly when they cannot (the auto-refund on an unscannable site
is better behaviour than most vendors manage). For the **Government Programme**: **no** — its
headline capability 404s. And nobody should be able to buy Pro Suite for SGD 29.
